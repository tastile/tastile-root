# ADR-0026: Phase B 受入基準 — 旧実装再現ではなく実用スケジューリングを正本とする

- 日付: 2026-11-26
- 状態: Accepted
- 対象: Tastile workspace 全体（Phase B / NF04-I02 以降の検証・移行・受入設計）
- 関連 issue: tastile-root#196、tastile-root#105（個人実用化 gate）、
  tastile-root#141（Native-first リリース計画 v0.4）、tastile-root#150（Muse 連携）、
  tastile-root#151（非破壊データ移行）、tastile-root#154（個人実用試験）

## Context

Phase B（既存 Muse 運用から新しい Tastile 環境への移行）で、作業が
「旧実装の出力一致・意味論的同等性」を最上位の受入基準として扱う方向に
流れていた。匿名化 fixture replay の exact-match 率、旧アルゴリズムとの
differential oracle、旧環境 expected-placements を正解とする検証がその例である。

しかし Tastile の目的は、旧 Tastile / Muse の過去のアルゴリズムや操作手順を
再現することではなく、**実際の生活において有用なスケジュールを生成し、
継続的に管理・調整できるシステムを完成させること**である（#141 の目的節と
整合）。旧実装を正解とすると、旧実装の不具合・回避操作・非効率まで
「正しい挙動」として固定してしまう。

## Decision

### 受入基準の正本

Phase B 以降の受入判定は、Tastile 自身のドメインモデルとスケジューリング
仕様（`tastile-core/v1/`、`specs/`、関連 ADR）から導出した基準を正本とする。
評価対象は次を含む。

- 現実の生活上の要求（学期・期間・優先度・期限・突発予定・中断・未完了・
  時間変動）を適切に表現できること
- 宣言された必須制約を満たし、実行可能で有用なスケジュールを生成できること
- 予定変更・遅延・再調整に対して状態が整合し、運用が継続できること

必須制約と最適化目標は区別する。制約違反は不具合、最適化目標の差は
品質評価の対象であって旧実装との差異そのものを不具合とはみなさない。

### 旧実装の位置づけ

- 旧実装の出力・手順は**参考資料**であり、受入判定の正解（oracle）ではない。
- 匿名化 Muse fixture は「現実的な生活上の要求を含む入力資料」として利用する。
  fixture 内の expected-placements は旧環境の参考出力であり、Tastile の
  出力との一致を要求しない。
- 旧環境固有の制約・挙動・回避操作（手動修復、補完タイル、特殊な再生成手順
  等）は、その必要性自体を再評価し、継承を前提としない。
- 既存データの保全（#151）と、生活上の要求を表現する能力は維持する。
  データを失わないことと、旧アルゴリズムの挙動を再現することは別の要求である。

### 検証基盤の再構成

- Lean 4 / property-based test / differential oracle / fixture は目的別に
  使い分ける。形式的証明はモデル自身の正当性・不変条件・制約充足・
  状態遷移を対象とし、旧アルゴリズムとの一致は証明対象にしない。
- スケジュール品質の評価は、必須制約充足と最適化目標を分けた基準で行う。
  具体的な評価基準・fixture の利用方法・oracle の再定義は後続 Issue で設計する。

### Muse との運用設計

Muse の既存運用をそのまま移植するのではなく、新しい Tastile の能力を前提に
理想的な運用を設計する。Muse が生活上の要求を登録し、Tastile がスケジュールを
生成・維持し、Muse が必要に応じて状況や意図を更新できる構成を目指す。
責務境界は既存のドメイン設計を踏まえて確定する。

## Consequences

- fixture replay 等の旧出力比較は「差異の分類・原因分析」の道具としては
  有効だが、完了条件・PASS 判定の根拠にはしない。過去の証跡
  （`tastile-core/docs/evidence/2026-11-16-muse-fixture-replay/` 等）は
  歴史的記録として保持し、数値目標として再利用しない。
- 「旧実装と一致した」「exact-match が増えた」を進捗指標にしない。
  進捗は「生活要求を満たすスケジュールを継続的に生成・調整できる」ことの
  証拠で測る。
- #105 の G0〜G5 gate（最低 7 暦日の shadow・隔離 mutation E2E・実用性評価）
  は実用性を測るものであり本 ADR と整合する。#150 の「現行操作を欠損なく
  実行可能」は能力カバレッジの要求であり、出力一致の要求ではない。
- 旧実装の不具合を補うためだけに存在した運用手順は、必要性の再評価なしに
  新環境へ持ち込まない。
