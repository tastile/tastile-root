## 2. 運用・デプロイ条件（Native-first 前提）

- api / worker は同一 tarball から取得し、`TASTILE_DATABASE_URL`（PostgreSQL 16 系）・`TASTILE_API_PORT`・`TASTILE_DELIVERY_PROVIDER` 等の環境変数で起動する。worker は `worker booted` ログと `/v1/ready` で健全性を確認する。
- migration は `migrate_run`（事前確認は `migrate_dry_run`）。fresh DB・既存 DB 双方の適用経路を検証済み。downgrade は提供しない（rollback は「旧 binary が新 schema で動く」前方互換のみ検証済み）。
- S4 実測（1,000 registered users / 554,389 placements / DB 963MB / WAL 累計 ~27.4GB / 定常 read p50=11ms p95=45ms p99=707ms）は resource-model §13・hosting-evaluation §7 Lane P が正本。**1,000 registered ≠ 1,000 同時 active**。高 active 率負荷・長期容量成長は未実測であり、VPS 構成の最終推奨は保留のまま。
- 初期 fill（新規 owner の 32 日 horizon materialization）は worker が非同期に実行する。新規 owner の初回 Timeline read は coverage 完了まで数秒かかり得る（#548、受入可能と判定済み・追加最適化は後続）。

## 4. 既知の制約と後続 Issue（core 側、スコープ外として保持）

- **#546**: idempotency tombstone 契約（idempotency TTL は OFF 維持。37 種 CommandPayload の非冪等性監査済み）
- **#547**: dead-letter archive の長期保持・再投入・診断ポリシー

- domain_event retention OFF（#503 系の retention 基盤は実装済み・フラグ OFF）、長期容量・高 active 率は未実測

## 5. Native-first 正式運用で次に決めること

1. **配備形態**: 単一 VPS での api+worker+PG 同居か、PG 分離か。S4 実測と Lane P の保守的試算を入力にするが、VPS 最終推奨は高負荷実測が揃うまで保留。
2. **初期 fill 運用**: 大量登録時の worker 収束時間・read 影響を運用手順（段階的 onboarding 等）に落とすか。
3. **client 統合順序**: Android（契約整合済み）→ Web（pin 更新 + 型再生成が前提）→ Desktop（契約経路の確立が前提）。CLI は core 同梱バイナリで当面代替可能か判断。
4. **未検証領域の扱い**: GitHub Actions billing 復旧後の CI 再実行要否、独立レビュー認証の復旧、Lean/differential oracle の継続 gate。
